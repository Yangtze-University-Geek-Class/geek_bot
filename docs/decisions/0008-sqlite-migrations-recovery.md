# ADR-0008：数据：SQLite 版本化迁移只扩不缩；GitHub 标记注释可重建状态；每日恢复校验

> control 的 SQLite 用编号的 SQL 迁移加 `PRAGMA user_version`，只扩不缩，让上一版镜像仍能读库；每条写入带隐藏标记，库丢了能从 GitHub 重建关键状态；备份每天自动恢复校验。

状态：`accepted` · 更新：2026-09-26 · 适用：control 的数据库、迁移、备份与恢复、outbox（由 #3、#9 实现，备份演练与异地副本见 #20）

## 背景

- control 是库的唯一写入者（[ADR-0003](0003-single-writer-control.md)）；preview 和 production 各一个库。
- 这是别人也会部署的产品：每个实例的库都要能随版本自动升级，没有人替部署者手工改库。
- 回滚是把环境切回更早的镜像 digest，不重置数据库（[RELEASES](../conventions/RELEASES.md)「回滚」）；这要求上一版镜像能读新版迁移过的库。
- 只用 `CREATE TABLE IF NOT EXISTS` 建表时改不了已有的列，已部署的库没法升级。
- 对 GitHub 的写入可能在超时后结果未知：盲目重发会重复评论，直接放弃又会漏写。
- 控制面常常只跑在一台主机上，磁盘和整机都可能出事（第一台节点的宿主条件见运维记录）；没有恢复过的备份不能算数。

## 决策

### 存储

- SQLite，WAL、`synchronous=FULL`、`foreign_keys=ON`。库文件在 control 的命名卷上，不改成宿主目录（[CODE-REVIEW](../conventions/CODE-REVIEW.md) 第 5 项）。
- 任务的原始事件不进库：按任务写成压缩的 JSONL 文件，保留 30 天、总量有上限；库里只存摘要。表清单见 [data-model](../services/control/data-model.md)。

### 迁移

- 迁移文件放在 `app/control/src/db/migrations/NNNN_*.sql`，按编号顺序执行，执行后更新 `PRAGMA user_version`。
- **只扩不缩**：迁移只加表、加列、回填数据；不删表、不删列、不改列的类型或含义。不再使用的列留在库里。确实需要收缩时另写 ADR。
- 迁移前自动备份。
- 「库版本比代码新时拒绝启动」按下面的意思实现，不能挡住回滚：
  - 库里除 `user_version`（执行到第几号迁移）外，另记一个兼容版本；只有收缩类的改动才抬高它；
  - 代码启动时，兼容版本比代码认识的新，就拒绝启动；
  - 只扩不缩的迁移不抬高兼容版本，所以上一版镜像打开新库仍能启动、能读写。
- 就绪检查 `/readyz` 按同一套规则判断：兼容版本 K ≤ 代码版本 C，而且已执行的迁移 D ≥ C（没有待执行的迁移）。回滚到上一版镜像时 D > C、K ≤ C，健康门照样能过。完整的就绪条件见 [API](../architecture/API.md) A-54。
- 兼容版本的具体表示由 #3 定稿：记在 `schema_migrations.compat_version`，库当前的兼容版本是编号最大那一行的值；迁移文件首行声明 `shrink=`（[data-model](../services/control/data-model.md)「迁移规则」）。「上一版代码打开新库能启动、能读写」由 `tests/control/server.test.ts` 证明。

### 备份与恢复校验

- 用 better-sqlite3 的在线 backup 做备份：每天一次，另外在部署前、迁移前各一次。备份用备份加密密钥加密并计算 sha256；保留 7 份每日备份加 4 份每周备份。
- 每天自动把最新备份恢复到临时文件，跑 `PRAGMA integrity_check` 并核对各表行数，失败就告警。
- master key 和备份加密密钥都是以 `*_FILE` 只挂给 control 的密钥文件，都不进备份（[SECURITY](../architecture/SECURITY.md) S-17 与密钥表）。可选的异地副本只存加密后的文件，放在外置盘或 NAS 目录（#20）。
- 恢复先用 `restore --dry-run` 演练核对，再由获授权的人执行（control 的 CLI，#3）。

### outbox：可去重、可核对

- 每条 GitHub 写入先进 outbox，同一次逻辑写入只有一条有效记录。状态机、各状态的含义和 `dedupe_key` 的组成只在 [write-whitelist](../services/control/write-whitelist.md)「幂等与 outbox」一节定义，[data-model](../services/control/data-model.md) 照抄，本篇不另列。
- 本篇只定这几条原则：`unknown` 表示请求发出去了但结果未知（临时错误重试用完也进 `unknown`），这类记录不盲目重发，先按隐藏标记（[ADR-0005](0005-rules-from-base-branch.md)）到 GitHub 查这条写入是否已经存在，再决定记为 `confirmed` 还是重发；`failed` 表示 GitHub 明确拒绝，不自动重试。
- 发送前再复核一次 GitHub 的当前状态：head 没变、issue 没被人重开、权限仍然足够。

### 从 GitHub 重建

- 每条写入都带 `<!-- geek-bot v1 env=… kind=… task=… sha=… round=… -->`。库丢失又没有可用备份时，control 按这些标记从 GitHub 重建追问轮次、已审过的 head、关闭状态和机器人分支。
- 有备份时先恢复备份，再按标记补齐备份之后的写入。
- 重建不了、只能从备份恢复或重新配置的：管理员与会话、机器人令牌（重新绑定）、节点登记与节点令牌（重新添加）、模型池、设置、审计日志。
- 标记里的 `env=` 让同一个机器人账号在两个环境的写入互不混淆。

## 替代方案

- **只用 `CREATE TABLE IF NOT EXISTS`**：改不了已有的列，已部署的库无法升级。
- **引入 ORM 或迁移框架**：新增生产依赖，没有必要（[STACK](../design/STACK.md)「不采用」）。
- **写降级迁移（down migration）支持回滚**：在真实数据上删列、改表风险大；只扩不缩加上按 digest 回滚已经够用。
- **库版本比代码新就一律拒绝启动**（按 `user_version` 直接比较）：回滚时库已经被新版迁移过，一律拒绝就等于不能回滚；改为只比较兼容版本。
- **只靠备份，不从 GitHub 重建**：备份最多落后一天，这一天里的写入会被当成没发过而重发。
- **改用 PostgreSQL 等独立的数据库服务**：多一个要部署、备份和升级的服务；单写者的规模用不上。

## 后果

- 库里会积累不再使用的列和表，这是有意的代价。
- 每个迁移都要测试「上一版代码能读写新库」；新代码要容忍回滚期间旧代码写入的、新列为空的行。
- 每天的恢复校验能及早发现备份损坏；恢复演练与异地副本的操作写进 BACKUP（#20 写入）。
- 重建依赖隐藏标记还在：人删掉了机器人的评论，对应的状态就丢了。
- 事件原文 30 天后删除，更早的任务只留摘要。
- 库文件、备份和事件文件里有仓库内容和任务输出，按实例数据对待：不进仓库、不进镜像、不进日志。

## 实施状态

- #3（已实现）：数据库层（`app/control/src/db/`）、迁移执行与启动时的兼容检查、迁移前备份、加密备份（AES-256-GCM 加 sha256）、`restore --dry-run`、`verify-backup`、每日恢复校验与告警、保留策略（7 份每日加 4 份每周，其余种类各 3 份）。正式恢复没有实现，随 #20。
- #9：outbox、隐藏标记、结果未知时按标记核对。
- #16：追问线程的状态机，以及按标记重建追问轮次与关闭状态。
- #20：异地副本、恢复演练，BACKUP 与 RUNBOOK。

## 重新评估条件

- 写入量超出单写者 SQLite 的能力（实测）；
- 需要控制面高可用或多个 control 实例；
- 出现必须收缩表结构的需求。
