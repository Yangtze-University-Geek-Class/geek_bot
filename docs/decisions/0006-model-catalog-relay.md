# ADR-0006：模型目录只读 catalog 文件；密钥只在 control；每任务令牌中继

> 可用模型只来自部署者挂载的只读 catalog 文件；模型网关密钥只在 control；sandbox 和 VM 用每任务令牌经节点、再经 control 中继访问模型；降级分 omp 进程内和 runner 外层两层。

状态：`accepted` · 更新：2026-09-26 · 适用：catalog 文件契约、模型池、模型中继、每任务模型令牌与降级记录（由 #13、#14 实现）

## 背景

- 所有者定下：模型按任务类型分池，池内按顺序降级（报错、超时、限流、中断时换下一个）；思考档位来自一份由所有者自己的同步工具生成的 catalog 文件，使用方只读这份文件，不另建模型表；网关密钥不进 VM。
- 产品面向任何部署者：各人用自己的 OpenAI 兼容网关（文档里写 `https://gateway.example.com/v1`）和自己选的模型，产品代码不内置具体模型和网关地址。
- sandbox 和 VM 运行不可信内容，不能持有网关密钥（[SECURITY](../architecture/SECURITY.md) S-02）。
- omp 进程内的 `retry.fallbackChains` 只处理瞬时错误；本轮已经有输出后才失败时，omp 以退出码 1 结束，不会自己降级（[runner 服务契约](../services/runner/README.md)「已知限制」）。

## 决策

### 模型目录

- 目录只来自挂载的只读 catalog 文件。不建模型表，不请求网关的 `/v1/models`。
- 文件契约是 `packages/protocol` 里的 JSON Schema（#13 写入），形状如下：

  ```text
  {version, generatedAt, provider:{baseUrl, apiStyle:"openai"}, models:[{id, name, contextWindow, maxTokens, efforts?:string[], compat?:{...}}]}
  ```

- 没有 `efforts` 的模型只提供 `off` 档位。
- catalog 只提供模型列表，不决定请求发往哪里。网关地址由部署配置 `GEEK_BOT_MODEL_GATEWAY_URL` 固定；catalog 里的 `provider.baseUrl` 与它不一致时，control 拒绝加载这份 catalog，并在后台告警。catalog 文件因此算作进入 control 的外部输入，按 schema 校验（信任边界见 [SECURITY](../architecture/SECURITY.md)）。
- 任何人都可以按这份 schema 手写 catalog，或用脚本生成。所有者自己的实例用所有者已有的同步工具生成，geek_bot 只是只读的使用方；在那套工具的说明里登记 geek_bot 这个使用方、怎样把文件送到控制主机（例如定期推一份只读副本），都属于实例运维，不写进本仓库。

### 模型池

- 按任务类型分池：审查、分诊、跟进、修复、返工、规则画像。池里每一项是 catalog 里的一个 id 加一个思考档位，按顺序排列；越界的档位服务端拒绝保存。
- catalog 里消失的模型在后台标红。
- 保存池配置时生成 omp 的 `modelRoles` 和 `fallbackChains`，并写审计。
- 产品不内置任何模型；实例的初始池由部署者在后台配置。

### 密钥与中继

- 网关密钥以 `*_FILE` 文件只挂给 control（S-02）。
- 请求路径：sandbox 经 unix socket（容器内有一个从回环地址到 socket 的转发器）、VM 经 guestfwd，访问节点的本地模型代理，请求带每任务令牌；节点附上自己的节点令牌，转发到 control 节点 API 下的模型中继（[节点协议](../services/node/protocol.md)）。
- control 核对：任务令牌与租约对应、模型在本任务的池里、请求数和 token 预算没用完、任务仍在运行；请求体只放行字段白名单里的字段（细节见节点协议）。通过后换成网关密钥，转发到 `GEEK_BOT_MODEL_GATEWAY_URL`，流式返回。
- 每任务模型令牌限定池内模型、请求数和 token 上限，租约结束即吊销；库里只存哈希。
- control 记录每个请求的模型、HTTP 状态、耗时和用量。这份记录是降级记录里可信的一方；runner 自报的记录另列，后台时间线标明来源。

### 降级

- 第一层：omp 进程内的 `fallbackChains` 处理瞬时错误。
- 第二层：本轮已经有输出后才失败时，runner 按池换下一个模型从头重跑；修复任务重跑前先把工作区恢复干净（`git reset --hard && git clean -fdx`）。超时也换下一个模型，但整个任务的总墙钟不超过单次上限的 2 倍。
- 上下文溢出和主动取消不降级。
- 结果不符合 schema：用同一个模型带修复提示重跑一次，仍不合格就降级。
- 池走完就判失败，不自动重试，由人点「重新排队」。

## 替代方案

- **在库里维护模型表，或在后台手工补条目**：与「只读 catalog、不另建模型表」冲突，两处来源会漂移。
- **网关地址取自 catalog 的 `baseUrl`**（前一版写法）：catalog 由仓库外的工具生成、定期送到控制主机，文件一旦被改，网关密钥和随请求发出的私有代码就会被送到别处；地址改由部署配置固定。
- **请求网关的 `/v1/models`**：返回内容没有思考档位、上下文长度这些字段，各家网关的返回也不一致。
- **每个节点持有网关密钥直连**：密钥分布扩大到每台节点，就在不可信任务的旁边。只在以后远程节点到 control 的带宽成为瓶颈时，由所有者重新决定。
- **在控制主机上再跑一份 catalog 同步程序**：同一份目录出现两个生成方，容易漂移；geek_bot 只读结果。
- **只靠 omp 进程内降级**：本轮有输出后失败时 omp 不会降级。

## 后果

- 所有模型流量都经过 control：它的带宽和可用性决定任务能不能跑（[ADR-0003](0003-single-writer-control.md) 的单点风险在这里同样成立）。
- 部署者必须提供符合 schema 的 catalog 文件；文件更新后，池里引用了已消失模型的项被标红，任务跳过它们落到下一项。
- 每任务预算限住失控的消耗；control 的用量记录可以审计。
- 私有仓库的代码会随请求流到模型网关，数据外流的边界由部署者负责。
- 有的模型需要特殊的兼容参数（写在 catalog 的 `compat` 里）。缺了这些参数，多轮工具调用可能被网关拒绝，池里的这一项实际不可用。未验证，由 #13、#14 用真实网关验证。
- 外层降级是否正确，完全取决于 runner 对失败原因的分类；以 #14 的夹具测试为准。

## 所有者结论

接受：所有者 2026-09-26 答复「ADR 全部接受」，记在 #25。按本 ADR 执行（对应 #22 第 11 项）。
