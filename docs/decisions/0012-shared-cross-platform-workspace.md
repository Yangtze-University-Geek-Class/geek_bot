# ADR-0012：多渠道项目与需求共用一个机器池

> 一个实例管理共享项目、需求、任务和机器；渠道账号独立绑定，管理员授权资源，控制面统一调度和发布。

状态：`accepted` · 更新：2026-10-03 · 适用：#34 的产品范围、control、console、node、runner 和 protocol

## 背景

所有者在 #34 的需求讨论中明确扩大产品范围：代码渠道包括 GitHub 和 GitLab，消息渠道接收日常需求；所有用户先共用一个池，管理员分配，不考虑隔离团队。随后授权整体实现。

原设计把一个 GitHub 账号同时作为实例所有者和机器人。多渠道、多连接的共享平台不能继续把渠道凭据等同于后台身份。节点也不能按账号各建一套执行池。

## 决策

1. 一个实例只有一个共享工作空间。项目、需求、任务、机器和模型池统一存储、查询和调度。不新增 tenant、team、organization 或用户专属资源池。
2. 后台角色仍为 owner、operator 和 viewer。管理员身份沿用 GitHub 数字身份的 device flow；认领、登录和重新认证只取身份并撤销临时令牌。GitHub 代码连接另外授权 `repo read:org`；GitLab 和消息连接独立配置。
3. GitHub、GitLab、飞书和签名 Webhook 通过统一适配器接入。代码平台保留 issue 与 change 的原始来源，PR 和 MR 归为 change，但权限和端点不强行套用同一个平台的规则。
4. 日常需求先持久化，再关联项目，随后成为可执行任务。代码平台条目可以产生有稳定 item 关联的任务；模型自由文本不决定写入目标。
5. 项目监控、逐类处理开关和外部写入模式分开。新项目的 review、triage、fix 和 rework 全部关闭；打开由 owner 重新认证后授权。operator 可以关闭。自动处理仍检查静默窗口、任务去重、平台权限、条目状态和实际 head。
6. 管理员分配项目可用机器、标签、信任等级和资源上限。控制面在一个 SQLite 事务内检查槽位、CPU、内存和租约，再派发任务。私有项目只派给受信机器。
7. control 仍是唯一 SQLite 写入者和外部写入出口。平台凭据用独立随机 nonce 的 AES-256-GCM 密文存库；读取适配器和 publisher 在请求期间解密。node 和执行环境不持有平台凭据或模型网关密钥。
8. publisher 使用持久 outbox。结果未知先核对，不盲目重发。GitHub review 仅为 `COMMENT`；GitLab 仅评论。补丁只追加到本实例记录的机器人分支并开 PR/MR。批准、合并、主干、tag 和禁止修改路径的边界不放宽。
9. 后台构建产物由 control 同源托管。样板数据模式只能开发和浏览器回归，写操作返回 405，不能当作实际平台的成功响应。

## 取代范围

本决策取代 ADR-0001 中“产品只有 GitHub 单账号入口”的范围，以及 ADR-0002 中“默认登录即绑定同一个机器人账号”的耦合。ADR-0002 的数字身份、令牌最小权限、认领、会话、重新认证和撤销约束保持。

ADR-0003 的单进程单写者与节点只出站保持；其“唯一 GitHub 写出口”推广为所有受管外部平台的 publisher 出口。ADR-0004、ADR-0005、ADR-0006、ADR-0007、ADR-0008、ADR-0009 和 ADR-0011 的安全、隔离和发布条件不因此放宽。

## 替代方案

- 每个平台另建任务系统和执行池：重复认证、调度和恢复规则，不能统一管理需求。不采用。
- 按每个用户或团队分租户：增加数据隔离、资源配额和授权规则，与所有者当前明确要求不符。不采用。
- 让 runner 持渠道令牌并直接写回：执行不可信仓库代码会扩大凭据泄漏与越权范围。不采用。
- 把样板界面作为交付：不能证明真实持久化、权限或任务处理。不采用。

## 后果

管理员邀请 viewer 就允许其查看实例共享数据，不能宣称按每个人的平台权限隔离可见内容。渠道账号的权限只是上限，项目开关、模式上限和任务能力继续取更严格条件。

后台登录仍需要部署者配置 GitHub OAuth App。只使用 GitLab 的部署者也需要该身份入口；改成本地账号或其它登录方式需要独立身份决策，不在本次实现里暗中替换。

## 实施和验证

#34 的源码落在五个原有工作区包，没有新增服务或第三方生产依赖。跨包类型与 schema 在 `packages/protocol/src/shared.ts`；第二个版本化迁移扩展共享平台数据；既有迁移不回改。

本机真实 HTTP 与 SQLite 已验证项目发现、同步、需求派发、角色拒绝、一次性节点令牌重放拒绝、租约栅栏和重启持久化。Ego 已验证真实生产模式后台的桌面和 390px 页面操作。外部接口使用隔离协议服务，不能代替真实账号授权或上线验收。

真实外部发布、node / sandbox 镜像、Linux/KVM 探针和任务、硬件健康和隔离仍需相应授权及设备验证，不标为通过。发布、合并和部署继续由原规范单独授权。

## 重新评估条件

出现团队数据必须隔离、不同来源独立机器池或无需 GitHub 的后台身份需求时再提出新决策。不要为了将来可能出现的需求提前加入多租户或改变现有信任边界。
