# ADR-0010：本仓库开发流程用的追踪记录头

> 本仓库 issue / PR 评论里的追踪记录统一用 `<!-- track v1 kind=… stage=… -->`，与产品内置的默认格式一致；产品代码里它只是可配置的默认值。

状态：`accepted` · 更新：2026-09-26 · 适用：本仓库的 issue / PR 追踪记录、[TRACKING](../conventions/TRACKING.md)、`scripts/task.mjs`、`.github/workflows/issue-lifecycle.yml`，以及产品的默认记录格式

## 背景

- 追踪记录头可以不带前缀，也可以带一个前缀（组织缩写或产品名）。[ADR-0001](0001-standalone-product.md) 规定代码和文档不写死任何组织专属格式，仓库以后也可能公开。
- #22 第 4 项推荐的是带组织缩写的前缀，公开安全检查对 TRACKING 和 issue-lifecycle 放行这个词；另一个选项是带产品名的 `geek-bot:track v1`。
- 所有者 2026-09-25 对 #22 第 4 项的回复（记在 #22 的第二条评论里）：「是统一规范，不一定非要加组织缩写什么的」。原话里是组织的英文缩写，因为这个词不能入库，引用时换成「组织缩写」。

## 决策

- 追踪记录头写成 `<!-- track v1 kind=<类型> stage=<阶段> -->`，放在评论第一行；`kind`、`stage` 的取值与正文格式以 [TRACKING](../conventions/TRACKING.md) 为准。
- 机器人写的记录可以在 `stage=` 之后追加可选属性 `actor=bot model=<id> effort=<档位> commit=<40 位 SHA>`，仍然是 v1；解析方必须忽略不认识的属性。
- 本仓库的开发流程与产品内置的默认格式一致，用自己的仓库验证产品的默认格式。
- 产品代码里这个记录头是可配置的默认值，不写死；目标仓库有自己的追踪格式时照它的格式写。
- 产品每条写入另带一行隐藏标记 `<!-- geek-bot v1 ... -->`（[ADR-0005](0005-rules-from-base-branch.md)）。这是产品标识，用于幂等和从 GitHub 重建状态，不属于追踪规范，两者不能互相替代。

## 替代方案

- 带组织缩写的前缀：仓库里会出现组织缩写，公开安全检查要为它开放行口子，也与 ADR-0001 冲突。所有者否决。
- 改成 `geek-bot:track v1`：前缀里带产品名，其它仓库采用这套规范时也得带上别人的产品名，不符合所有者「统一规范」的说法；而且和产品隐藏标记 `geek-bot v1` 容易混淆。不采用。

## 后果

- [TRACKING](../conventions/TRACKING.md) 的记录格式、`scripts/task.mjs` 的开工记录、`issue-lifecycle.yml` 的合并关闭记录都用 `track v1` 记录头，在 #1 里同步改好。`scripts/pr-contract.mjs` 只核对 PR 正文、不写追踪记录，不受影响。
- 公开安全检查不需要为追踪前缀放行任何组织词。
- 本决策之前写下的评论（例如 #22 的第一条评论）仍是旧前缀，不回改；此后的新记录只用 `track v1`。
- 产品侧可配置的默认格式随 #9（publisher 按模板生成记录头）和 #10（内置默认规范）实现。

## 实施状态

- #1：规范文档、脚本与工作流按本决策写。
- 产品代码：#9、#10。

## 重新评估条件

- 需要不兼容地修改记录头字段时，升到 `v2`，不改变 `v1` 的含义。
