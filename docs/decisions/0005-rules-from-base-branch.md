# ADR-0005：规则来源只信 base 分支；机器可执行字段只来自结构化配置

> 仓库规则从 base 分支按 blob sha 读取，PR 改不了审查它自己的规则；影响写入的字段只取自结构化配置，能力开关以后台为基准、仓库只能调低；每条写入另带产品隐藏标记 `<!-- geek-bot v1 ... -->`，它和追踪记录头 `track v1` 是两回事。

状态：`proposed` · 更新：2026-09-26 · 适用：control 的规则读取与规则画像、任务包里规则文件的覆盖、publisher 生成的记录头与隐藏标记（由 #10、#9 实现）

## 背景

- 所有者定下：每个仓库按自己的规范工作，来源是仓库的配置文件和规范文档，再加上后台的覆盖；没有规范时用 geek_bot 自带的默认规范，默认规范可以在后台修改。
- PR 可以修改 `AGENTS.md` 这类规则文件，而 omp 会自动加载工作目录里的 `AGENTS.md`。如果从 PR head 读规则，一个 PR 就能放松对它自己的审查（[SECURITY](../architecture/SECURITY.md) S-05、S-08）。
- 让模型把散文规范读成可执行规则，结果不可审计，也容易被提示注入。
- 在公开产品里，仓库维护者应该能约束机器人在自己仓库里的行为；部署者的后台设置不应该替仓库放宽限制。
- 写入要能去重、能认出自己写过什么、库丢失后能重建状态（[ADR-0008](0008-sqlite-migrations-recovery.md)），需要一个固定、不随仓库格式变化的产品标识。追踪记录头 `track v1` 是可配置的默认值，仓库有自己的格式时会被替换（[ADR-0010](0010-tracking-record-prefix.md)），担不了这个角色。
- 目标仓库的入口规则常要求「先读完全部规范」，审查任务照做会让 token 成本和耗时成倍增加（#22 第 14 项）。

## 决策

### 从哪里读

- 规则文件一律从默认分支（或该仓库配置的 base 分支）按 blob sha 读取、按 blob sha 缓存，**从不**从 PR head 读取。
- 读取的文件：
  - `.github/geek-bot.yml`；
  - `AGENTS.md`；
  - `CONTRIBUTING*`；
  - `.github/pull_request_template.md`；
  - `.github/ISSUE_TEMPLATE/*`；
  - `AGENTS.md` 链接到的、文件名匹配 CODE-REVIEW、PULL-REQUESTS、ISSUES、COMMITS、BRANCHING、TRACKING 的文档。
- 目标仓库的 base 分支上没有 `CONTRIBUTING*`、issue 模板或 PR 模板时，回退到所在组织（或账号）`.github` 仓库默认分支上的同名文件。这是 GitHub 自己的默认社区文件机制，geek_bot 按同一套规则回退（[Creating a default community health file](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/creating-a-default-community-health-file)，2026-09-26 核对）：
  - 仓库自己有对应文件，就不用默认文件；
  - 仓库在自己的 `.github/ISSUE_TEMPLATE` 里定义了有效的 issue 模板或模板配置，默认的 issue 模板目录整个不用；
  - GitHub 只认公开的 `.github` 仓库，geek_bot 同样只读公开的；读不到就跳过这一层。
- 每份最多 64 KB，合计最多 256 KB，超出的部分不读。
- 打任务包时，head 快照里的 `AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING*`、`.github/*template*`、`.github/geek-bot.yml` 一律换成 base 上的版本；base 上没有的，从任务包里删掉；子目录里的同名文件同样处理。PR 对这些文件的修改只出现在待审的 diff 里，不会成为 omp 实际加载的规则。
- 任务包另外剔除 `.omp/`、`.claude/`、`.cursor/`、`mcp.json`、`.env*`（S-04）。

### 机器可执行的字段

- 机器可执行的字段包括：分支模板、base、PR 正文段落、追踪记录格式、受管标签、禁改路径、校验命令、需要的节点标签，以及能力开关和写入模式。它们只从结构化来源取值，共有四层：
  1. 仓库的 `.github/geek-bot.yml`（base 分支上的版本）；
  2. 后台对这个仓库的覆盖（改仓库覆盖只归 owner，要重新认证，见 [SECURITY](../architecture/SECURITY.md) S-09）；
  3. 所在组织 `.github` 仓库里的同名文件；
  4. geek_bot 内置默认，可以在后台修改（默认值见 [behavior](../services/control/behavior.md)）。
- 不同字段的合并方式：
  - **能力开关（审查 PR、受理 issue、自动修复、返工）和写入模式**：以后台对这个仓库的值为基准；仓库的 `.github/geek-bot.yml` 和组织 `.github` 这两层只能调低，不能调高；没设置的层不参与。仓库文件因此不能替自己打开写入。
  - **禁改路径**：各层取并集，内置默认项不能删（S-19）。
  - **出网白名单**：全局白名单只能由 owner 重新认证后扩大；仓库层只能缩小（S-14）。
  - **其余非安全字段**（天数、窗口、分支模板、PR 正文段落等）：按上面 1 到 4 的顺序，取第一个设置了的值。
- `.github/geek-bot.yml` 与规则画像的字段定义放在 `@geek-bot/protocol`（RepoProfile，#10）。

### 散文规范

- `AGENTS.md` 等散文规范只作为模型上下文，不由模型解读成可执行规则。
- 可以跑一次规则画像提取任务，从散文里归纳出「建议画像」；其中凡是影响写入的字段，都要 owner 在后台确认后才生效。确认之前，这个仓库的修复通道保持关闭。
- 审查任务不强制遵守目标仓库「先读完全部规范」的入口要求：用追加的系统提示把审查限定为读与审查相关的规范和相关服务文档，控制 token 成本。每个仓库可以关掉这项精简（#22 第 14 项）。

### 记录头与隐藏标记

- 追踪记录头由 publisher 按仓库画像里的模板生成，模型只能填字段。仓库没有自己的格式时，默认是 `<!-- track v1 kind=<类型> stage=<阶段> -->`（[ADR-0010](0010-tracking-record-prefix.md)、[TRACKING](../conventions/TRACKING.md) §6）。
- publisher 的每一条写入（评论、review、新开的 issue、PR 正文）另带一行隐藏标记：

  ```text
  <!-- geek-bot v1 env=<env> kind=<kind> task=<id> sha=<head12> round=<n> -->
  ```

  标记单独占一行，放在正文最后一行，不占追踪记录头要求的第一行。仓库有自己的记录格式时照它的格式写，再附加这一行。
- 隐藏标记的用途：
  - 幂等：outbox 里结果未知的写入，先按标记到 GitHub 查它是否已经存在，再决定是否重发；
  - 认出自己的写入：轮询时带标记的评论算机器人写入，不重置静默窗口；publisher 只允许修改带自己标记的评论；
  - 重建：库丢失时，按标记从 GitHub 重建追问轮次、已审过的 head 和关闭状态（ADR-0008）。
- 隐藏标记和追踪记录头的区别：

  | | 追踪记录头 `track v1` | 隐藏标记 `geek-bot v1` |
  |---|---|---|
  | 性质 | 追踪规范，给人和 Agent 读进展 | 产品标识，给 geek_bot 自己读 |
  | 能否改 | 可配置的默认值；仓库有自己的格式时被替换 | 格式固定，不随仓库格式变化 |
  | 位置 | 评论第一行 | 正文最后一行 |
  | 谁解析 | 读追踪记录的脚本与 Agent，只看记录头 | control 的 outbox、轮询与重建逻辑，只看标记 |

  两者不能互相替代：解析追踪记录不看隐藏标记，幂等和重建不看记录头。
- 发布前删除模型文本里的 HTML 注释（S-05 的输出中和）；记录头和隐藏标记只由 publisher 生成。

## 替代方案

- **直接用 PR head 的规范**：PR 可以借改 `AGENTS.md` 放松对自己的审查。
- **让模型把 `AGENTS.md` 解读成可执行规则**：不可审计，容易被提示注入。
- **非安全字段让后台覆盖优先于仓库文件**：公开产品里，仓库维护者应该能约束机器人在自己仓库里的行为，所以仓库文件排第一。
- **能力开关和写入模式也按 1 到 4 的顺序取值**：仓库文件排第一，就能替自己打开写入；改为以后台的仓库值为基准，仓库和组织两层只能调低。
- **能力开关和安全限制在各来源之间简单「取更严」**（前一版写法）：没设置的层算最严还是最松说不清，出网白名单的扩大也没有归属；改为上面按字段分别规定。
- **不回退到组织 `.github` 的默认社区文件**：所有者要求没有自己规范的仓库用组织的默认规范，GitHub 本身也按这套机制回退，不回退会与仓库在 GitHub 上看到的模板不一致。
- **读取 `AGENTS.md` 链接到的全部文档**：成本高，提示注入的面也更大；限定文件名和大小已经覆盖审查需要的规范。
- **拿追踪记录头兼作幂等标识**：记录头可配置、会被仓库格式替换，人也可能照抄进自己的评论，不稳定；ADR-0010 已写明两者不能互相替代。
- **隐藏标记放在正文第一行**（架构草案的写法）：与 [TRACKING](../conventions/TRACKING.md) §3「每条评论第一行是记录头」冲突。
- **完全遵守目标仓库的入口规则**：token 成本高、耗时长（#22 第 14 项的另一个选项）。

## 后果

- 规则改动要合进 base 分支后才生效；修改规则文件的 PR 按旧规则审查，这是有意的。
- 没有 `.github/geek-bot.yml` 的仓库，修复通道要等 owner 确认画像后才开，多一步人工，换来写入不依赖模型的猜测。
- 读组织 `.github` 仓库需要读权限；读不到就跳过这一层。组织改了默认社区文件，会同时影响组织里所有没有自己对应文件的仓库。
- 隐藏标记在 GitHub 网页上看不到，但在评论原文和 API 里可见。它只含环境名、任务 id、短 SHA 和轮次，不含密钥或内部地址。
- 人删掉了机器人的评论，这条评论对应的状态就没法从 GitHub 重建。
- 精简审查的读取范围可能漏掉入口规则里的要求；仓库可以关掉精简，代价是成本。

## 重新评估条件

- omp 提供可靠的开关，保证不自动加载工作目录里的规则文件；
- 仓库普遍要求机器人完整遵守自己的入口规则；
- 隐藏标记需要不兼容的改动：升到 `v2`，不改变 `v1` 的含义。
