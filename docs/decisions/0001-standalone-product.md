# ADR-0001：geek_bot 独立成可自部署的通用产品

> geek_bot 面向任何部署者，代码和文档不写死组织、仓库、主机、网段、网关和账号；env 模板只放占位符。

状态：`accepted` · 更新：2026-09-25 · 适用：整个仓库（代码、文档、测试、夹具、部署模板）

## 背景

- 这个机器人最初规划为所在组织主仓库 geek_main 里的一个包（`app/bot`），只服务那一个组织。所有者 2026-09-25 决定把它独立出来，做成大众都可以用的项目：部署者用一个 GitHub 账号（一般是小号）登录，这个账号就成为机器人，监控它能访问的全部仓库（#22）。
- 本仓库的开发规范体系来自 geek_main stage 0fa8dcc，按本仓库改写后放在 `docs/conventions/`（#1）。改写后的规范是本仓库唯一的现行规范，不再引用那边的文件。
- 那套规范的 AGENTS §3 要求部署 env 模板里「非密钥项（origin、主机、端口、路径）预填真实值，密钥由 CI 用环境级 secrets 填充」。照搬会让仓库里出现内部主机和网段，与「以后可能公开」冲突；而且免费计划的私有仓库没有 Environments，环境级 secrets 用不了（见 [CICD](../ops/CICD.md)）。
- 仓库目前私有，以后可能公开。

## 决策

- geek_bot 是独立仓库、独立产品，面向任何部署者：部署者在 Web 后台用一个 GitHub 账号登录，这个账号就成为机器人；它自动发现该账号能访问的所有仓库，按在每个仓库的实际权限审查 PR（只发 COMMENT）、受理和跟进 issue、在临时 VM 里修小改动并开 PR。批准与合并始终由人来做。
- 代码、文档、测试和夹具不写死组织名、真实仓库名、内部主机名、内网或组网地址、网关地址和真实账号名，也不写死任何组织专属的追踪记录格式。需要时写占位：`<owner>`、`<org>/<repo>`、`https://geek-bot.example.com`、`203.0.113.10`（RFC 5737 文档地址）。`pnpm check:public-safety` 在本地和 CI 里拦截已登记的模式（私网、CGNAT 与链路本地地址段，带 `.mesh.` 段的主机名，被禁词与个别地址的哈希）；通过不等于没有泄漏，其余靠审查（[CODE-REVIEW](../conventions/CODE-REVIEW.md) 第 9 项）。
- 原来所在组织的仓库只是 geek_bot 管理的普通仓库之一：不在那边加 `app/bot`、后端接口、控制台页面或机器人专属规范。
- 本仓库自己的开发流程沿用背景里那套规范体系：issue → task worktree → PR 回 `stage` → rc tag → 所有者验收 → 正式 tag（[BRANCHING](../conventions/BRANCHING.md)、[RELEASES](../conventions/RELEASES.md)）。
- **env 模板只放占位符和通用默认值**：`deploy/env/` 下的模板（随 #7 加入）和根 `.env.example` 不写任何实例的真实值；实例的真实非密值只在目标机的 `.env.<环境>` 里；密钥一律用 `*_FILE` 指向目标机上的密钥文件，模板里的密钥项只能留空或写 `*_FILE` 路径。这是对背景中 AGENTS §3 的有意偏离。#22 第 3 项推荐的就是这个做法；#22 约定各项默认按推荐推进，所有者 2026-09-25 回复时只改了第 4 项，对第 3 项没有提出修改（记在 #22 的第二条评论里）。#22 正文写明这一项在 #1 里批准，所以所有者的明确确认在 #1 的 PR 里给出。本仓库 [AGENTS](../../AGENTS.md) §3 按这一条写。
- 公开前必须同时满足：
  1. 所有者选定许可证，提交 `LICENSE`；
  2. 提交 `SECURITY.md`，写明私下报告漏洞的渠道；
  3. `pnpm check:public-safety` 在全仓库通过；
  4. 提交历史里没有内部信息（组织名、内部主机、网段、网关、账号、密钥）；
  5. 本仓库在 GitHub 上随公开一起变为可见的内容同样检查干净：issue 与 PR 的标题、正文和评论，标签说明，release 说明，Actions 运行日志。规则与第 3、4 项相同，做法例如用 `gh` 把它们导出成文本，交给 `scripts/check-public-safety.mjs` 导出的 `scanText` 按同一份被禁清单检查，再人工看一遍；命中的内容由所有者编辑或删除。
- 第 5 项做不到时（例如命中的评论太多、改不干净），不把本仓库原地改为公开：另建一个公开仓库，只推送满足第 3、4 项的历史，本仓库保持私有并归档。走这条路时，文档里的 `#n` 引用（例如「#22 的第二条评论」）在新仓库里不再指向原来的 issue，公开前要把这些引用改写成不依赖本仓库 issue 的说法。

## 替代方案

- 放进组织主仓库作为 `app/bot`（原方案）：与组织耦合过重，无法独立部署和公开。所有者 2026-09-25 否决。
- 做成组织主仓库的插件：同样无法独立部署和公开。
- env 模板照搬「非密钥项预填真实值」：仓库里会出现内部主机和网段，与「可公开」冲突。
- 另建一个私有运维仓库存放实例值：多一个需要同步的仓库；目前实例值只放在目标机就够用，暂不采用。

## 后果

- 移植过来的规范里凡与组织绑定的内容（域名、栈目录、镜像名前缀、组织专属追踪前缀、论坛和官网）都已改写或删除；与背景中规范体系的其它偏离，逐条记在对应的 ADR 或规范里。
- CI 只能用占位模板校验 env 字段契约；实例真实值是否正确，只能由部署脚本在目标机上核对（#7）。部署方式本身（ghcr 同一 digest 跨环境、目标机拉取式部署）另由 ADR-0007 写定（计划中，由 #2 写入）。
- 追踪记录头改为不带组织前缀的 `track v1`，见 [ADR-0010](0010-tracking-record-prefix.md)。
- 满足公开前条件之前仓库保持私有；不为了解锁分支保护、rulesets、Environments 等平台功能提前公开。

## 实施状态

- #1：规范文档、门禁脚本（含 `check-public-safety`、`check-secrets` 的 `*_FILE` 规则）、CI 与模板。
- env 模板、compose、部署与回滚脚本、`release.yml`：#7。
- `LICENSE`、`SECURITY.md`、公开前的全仓库与提交历史扫描，以及第 5 项 GitHub 上 issue、PR、评论、标签说明、release 与 Actions 日志的检查（或改走新建公开仓库的路线）：#21。#21 正文的「范围」目前只写了全仓库和提交历史，开工时要把第 5 项补进范围与验收条件。

## 重新评估条件

- 所有者决定只服务单一组织；
- 出现必须入库、又无法用「占位模板 + 目标机文件」表达的实例配置；
- 仓库公开后 GitHub 平台能力（Environments、分支保护）可用，需要重新决定部署授权方式时，另写 ADR。
