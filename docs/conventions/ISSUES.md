# Issue 规范

> issue 是一件事的主档：开发前先开 issue，写清现象、复现、环境与验收条件；之后每一步进展都以追踪记录留在评论里，PR 合并即关闭。

状态：`current` · 更新：2026-09-26 · 适用：本仓库的所有 issue，人与机器人账号都遵守。

## §1 开发前先开 issue

**任何 `task/<issue>/<slug>` 分支都必须先有对应 issue，紧急修复也不例外**：分支名要用 issue 号，`task.mjs start` 与 `pr-contract` 都要求 issue 存在且开着（[BRANCHING](BRANCHING.md)）。紧急时可以先开一个只写一句现象的 issue，马上用 `node scripts/task.mjs start <issue> <slug>` 开工，事后再补全正文。先查重再开新 issue：在 issue 列表按端、关键词、错误信息搜索（含已关闭），确认没有同一件事；重复的直接在原 issue 补一条「复现」记录。

**一件事一个 issue**：一个 issue 只描述一件可以独立验收的事。所有者一次提了几件事（例如「审查评论写明用的模型 + 空闲时轮询降频 + 后台加节点页」）时，能一起验收的放一个 issue，不能一起验收的拆开，互相 `Refs #n`。

生命周期、互相引用和评论格式见 [TRACKING](TRACKING.md)。要点：

| 关联 | 位置 | 要求 |
|---|---|---|
| issue → 分支 | `task/<issue>/<slug>` | 一个 issue 一条 task 分支 |
| PR → issue | PR 正文「关联」段 `Closes #<issue>` | 与分支号一致，CI 的 `pr-contract` 核对 |
| issue → PR | issue 表单里的「实施」字段（开 issue 时留空） | 开 PR 的人回填分支名、PR 编号；合并后补合并提交 |
| 进展 | issue 评论 | 按 [TRACKING](TRACKING.md) §3 的格式，每个阶段一条 |
| 谁来做 | 负责人（assignee）、`bot:manual` 标签 | 见 §5 |

**PR 合并进 `stage` 即关闭 issue**：`issue-lifecycle` 工作流自动关闭 issue，并在 issue 与 PR 上各留一条「关闭」记录；`branch-hygiene` 删除 task 分支。GitHub 自带的 `Closes #n` 只在合进默认分支 `main` 时生效，不能依赖它。工作流失败时，合并的人当场手工关闭并补记录。已合并的分支不再提交；后续问题开新 issue。

## §2 正文内容

标题：`<模块>：<用户可见的症状或诉求>`，模块取「端」的标签名。「端」就是 issue 模板里「端（主端）」下拉的取值，也是同名标签：`control` / `console` / `node` / `runner` / `protocol` / `deploy` / `docs` / `tooling`。跨端的事选主端，其它端在正文里写明。

issue 表单（`.github/ISSUE_TEMPLATE/`）只在进入默认分支 `main` 后出现（[CICD](../ops/CICD.md)「触发与职责」）；在那之前照本节手写各段，最后留一个空的「实施」段。

### 缺陷

| 段落 | 要求 |
|---|---|
| 现象 | 实际看到了什么：原文报错、截图（直接拖进编辑框上传）、录屏 |
| 复现步骤 | 最小路径，编号，每步写操作与看到的结果；偶发的写复现概率与已知条件 |
| 期望 | 应该是什么样 |
| 影响 | 谁会遇到、多严重、有没有绕过办法；决定优先级 |
| 环境 | 见 §3 |
| 证据 | 截图、录屏、报错原文、`requestId`、任务日志片段；不贴令牌、会话、节点令牌、完整请求头、真实数据或私有仓库的内容 |
| 验收条件 | 怎样算修好：可观察的结果，以及要在哪些环境、尺寸或节点上看 |

### 需求 / 改进

写使用场景、范围和**不做什么**、接口 / 权限 / 数据影响、验收条件。描述问题与期望，不写实现方案（方案写在 PR 的「解决链路」或 issue 的「方案」记录里）。依赖升级说明动机、官方迁移来源和回退策略，不把「最新版」当成唯一理由。

严重性按真实影响区分：阻断核心流程、数据或权限风险（包括机器人可能越权写入）为 P0；主要功能受损或已排期为 P1；其余 P2。未经复现的怀疑标为待确认，不以肯定语气写已证实的漏洞。

## §3 环境与设备

**必填**：

- 分支与完整 commit SHA（`main` / `stage` / `task/<issue>/<slug>`），不写不存在的分支名；
- 实例版本：正式 `X.Y.Z`，预发布 `X.Y.Z-rc.N@<sha12>`，能对应到发布 tag 时一并写上；版本取自后台页脚或 control 的版本接口（计划中，#3、#7），展示规则以 [RELEASES](RELEASES.md) 为准；本机开发写分支与 SHA 即可；
- 部署方式：本机、预发布实例还是正式实例；control 与出问题的 node 各是哪个版本。只写环境名，不写实例的内部地址或主机名。

**按问题类型补充**（与问题无关的不写，不为凑字段填）：

| 问题类型 | 需要的信息 |
|---|---|
| 后台布局、溢出、窄屏 | 视口尺寸（如 390×844）、设备像素比、浏览器与版本 |
| 登录、权限 | 身份（部署者 / 管理员）、登录方式；**不贴会话、令牌或 cookie** |
| 接口、数据 | 请求路径、状态码、`requestId`；不贴完整请求头和真实数据 |
| GitHub 相关（审查、受理、轮询、写入） | 机器人账号在目标仓库的权限级别（Read / Triage / Write / Maintain / Admin）、相关任务 ID、目标 issue 或 PR 用 `<org>/<repo>#n` 形式的占位描述；**不贴私有仓库的内容、不贴令牌** |
| VM、sandbox、节点 | 节点的 CPU 核数、内存、是否有 `/dev/kvm`、节点版本、任务 ID |
| 模型 | 任务类型、模型池、实际使用的模型与思考档位、降级记录；不贴网关地址和密钥 |

## §4 关闭与安全

关闭前 issue 上必须能查到对应 PR 与验证结果（自动「关闭」记录已包含 PR 与合并提交）；不能仅因代码存在或构建成功就关闭功能缺陷。放弃、重复、被取代的 issue 先发一条「关闭」记录写明原因再关。

安全问题私下报告，不开 issue，也不在 PR 或评论里写漏洞细节。正式的私下报告渠道还没有（`SECURITY.md` 与 GitHub 的私下漏洞报告随 #21 加入）；在那之前，直接私下联系仓库所有者。报告里同样不贴令牌、真实会话、完整请求头、实例数据库或私有仓库的内容。

## §5 分配与机器人

geek_bot 的机器人账号会处理没人认领的 issue（受理、追问、提醒、关闭、改写重开；计划中，#16 实现）。本仓库也按这套默认规则使用它。开 issue 的人用负责人和标签告诉它该不该接：

| 想要 | 怎么做 | 机器人的行为 |
|---|---|---|
| 让机器人来做 | 把 issue 分给机器人账号 | 接，优先于它自己发现的 issue |
| 自己或指定的人来做 | 把 issue 分给这个人 | 不接、不追问、不关、不改写；关联的 PR 照样审 |
| 人来做，但还没定是谁 | 打 `bot:manual` | 同上 |
| 让机器人自己判断 | 什么都不做 | 受理；小改动可能自己修 |

- `bot:blocked` 表示机器人追问后在等回复。回复（评论或修改正文）后由机器人自己去掉；人也可以直接去掉。默认第 5 天没人回复会提醒一次，第 7 天机器人关闭 issue；同一个 issue 最多追问 2 轮。
- 分配 issue、打标签需要仓库的 Triage 以上权限。没有这个权限的人，在 issue 里写明想让谁来做，由维护者分配。
- 机器人在 issue 最后一次变动后静默一段时间才处理它（默认 5 分钟）：负责人和标签在开 issue 后尽快补齐。
- 机器人可能关闭价值不高的 issue，或把说清楚了但不合本规范的 issue 改写成一个新 issue、再关闭原 issue；每次关闭前都会先留「关闭」记录写明原因。觉得关错了，直接重开；人重开过的 issue，机器人不再关。
- 机器人的写入限于：发评论和追踪记录、发 `COMMENT` 类型的 PR review、加减 `bot:*` 标签、关闭或新开 issue、推机器人自己的分支并开 PR（本仓库配置为 `task/<issue>/<slug>`；逐条清单见 [写入白名单](../services/control/write-whitelist.md)，#9 实现）。它不批准、不合并、不关 PR；它发的记录格式见 [TRACKING](TRACKING.md) §6。

上面的等待天数、追问轮数、静默时间都是产品默认值，部署者可以在后台修改。完整的默认行为（两条通道、优先级、等回复的计时、复核条件）见 [默认行为](../services/control/behavior.md)。
