# 人工验收记录模板

> 空白模板，供验收人逐字段手工填写；不是流水线自动生成的通过证明。

状态：`current` · 更新：2026-09-25 · 适用：在预发布实例试用某个 rc、决定是否发正式版之前；随 #7 首次使用

## 适用范围

字段取自 [RELEASES](../conventions/RELEASES.md) 对验收记录的要求。发版只靠打 tag：`vX.Y.Z-rc.N` 发到预发布实例，验收通过后 `main` 快进到同一提交并打 `vX.Y.Z` 发到正式实例。本模板用于「把 `main` 快进到这个提交、打正式 tag 之前」的人工试用记录：在预发布实例试用某个 rc tag 所在提交构建出的镜像。

发布镜像与部署脚本随 #7 加入，#7 第一次把 rc 部署到预发布实例时开始使用本模板；正式实例上线（#20）按它验收。在那之前没有可以验收的实例，不要预填。

## 重要限制

- **Agent 不得代填任何字段**，包括「试用范围/结果」「放行结论」这类看起来可以从 CI 输出推断的字段；机器验证通过（`pnpm verify`、CI 全绿）不是人工试用，也不能替代验收人的明确结论。
- **不得把已填写的验收记录存进被验收的提交本身**：在候选提交之后再追加一个引用它的验收文件会产生新提交，新提交不能冒用旧验收。记录保存在仓库提交历史之外、能追溯到验收人本人的地方（例如验收人本人在对应 issue 上发的评论），不进入 `main` / `stage` 的提交历史。
- **记录按公开内容写**：issue 评论对能读本仓库的人都可见，仓库公开后对所有人可见，不是有访问控制的地方。记录里不写真实账号名、私有仓库名、实例的内部地址和主机名、令牌、密钥和实例数据，规则与 [PULL-REQUESTS](../conventions/PULL-REQUESTS.md)「附件与证据」和 [TRACKING](../conventions/TRACKING.md) 相同；需要核对这些值时，在本机核对后写「已本地核对，不公开」。
- 本模板本身不代表任何实例已开通、已配置人工门禁或已具备发布授权。
- 预发布实例不用正式机器人账号写真实仓库：试用只在沙盒仓库里写，或只演练不写（[AGENTS](../../AGENTS.md) §5）。

## 空白字段

- 验收人：
- 时间（ISO 8601，含时区）：
- 目标环境（`preview` / `production`）：
- 被验收的 rc tag（`vX.Y.Z-rc.N`）与准备发布的正式 tag（`vX.Y.Z`）：
- 完整提交 SHA（40 位小写十六进制）：
- 后台显示的版本（后台页脚或版本接口显示的 `X.Y.Z-rc.N@<sha12>`，接口随 #7 确定）：
- 镜像 digest（rc 发布清单里的每个镜像各一个完整的 `sha256:` 值，逐个与清单一致；镜像按 #7（control）、#11（node）、#17（vmimage）陆续加入发布清单，以该 rc 实际的清单为准；正式发布时应当与这里验收的 digest 相同，不重新构建）：
- 试用用的 GitHub 账号与仓库（按角色写，不写真实名字：登录后台的账号是不是所有者本人；机器人账号是不是与正式实例同一个；沙盒仓库写成 `<org>/<repo>` 并注明是沙盒；写入模式是只写沙盒仓库还是只演练不写。真实账号名和仓库名写「已本地核对，不公开」）：
- 试用范围/结果（实际点击或操作了哪些路径，观察到的真实结果，不写「预计通过」）：
- 已知问题（没有就写「无」，不留空）：
- 回滚对象（发布失败时回滚到哪个更早的正式 tag 及其镜像 digest）：
- 放行结论（明确写「批准发布」或「不批准」，不写模糊措辞）：
- 审批记录链接（指向该次记录本身的可追溯链接，不是本文件）：

## 使用方式

验收人复制本模板，在记录系统里逐字段填写，不在本仓库内保存已填写的副本。填写完成、放行结论明确后，才能把 `main` 快进到被验收的提交并打正式 tag；执行人要核对记录里的提交、rc tag 和镜像 digest 与实际一致。正式 tag 推送后，由维护者按部署文档（#7 写入）在目标机部署同一 digest。
